01 · OrientationThe system in one picture

Before the changes, the context. This is a self-hosted audiobook manager for a household: one Node.js server in the house scans the family's audio files, enriches their metadata, and streams them to a Netflix-style web shelf used on phones and laptops. It runs offline-first, including on Android, and it never phones home with your library.

Three properties shape everything in this report:

  • Offline-first. The phone must keep working with the server unreachable: downloads live in an on-device replica, progress lives in an encrypted local cache before it ever reaches the server.
  • Multi-server capable. One household can own several servers; a device may see books from more than one catalogue. Identities that look interchangeable (“book #7”) are not — which turned out to be a live data-corruption class of bug (Phase 2).
  • Privacy by default. GDPR obligations are enforced in code (erasure, export, retention), not written down and hoped for — which is why the personal-data list is now a module with a test that reads the database schema (Phase 6).

02 · The findingWhy we intervened

An architecture review in November 2026 found nine “shallow module” smells. They share one recurring shape, and it is worth internalising before reading any of the changes:

A rule was extracted into a pure, tested function — but the code that runs kept its own copy of the rule. The test proves the function is right; it says nothing about whether the app calls the function, or a lookalike sitting next to it.

Nine concrete findings fell out of this shape. Appendix A of the spec numbers them; the report folds them into the phases that fix them. The ones that were live risks, not just untidiness:

  • Data corruption. Progress was keyed by bare book id; two servers holding book #7 overwrote each other’s resume position.
  • Compliance gap. The GDPR export omitted webAuthnChallenge, which the erasure route did delete — export and erase disagreed.
  • Invalid data reaching the database. 35 of 60 routes had no input schema; a position of NaN or a speed of Infinity could be written to a listener’s progress row.
  • Privacy leak. The AI prompt embedded item.filePath — the absolute server path of a family member’s files — and sent it to a third-party model.
  • Security posture. The admin console could page raw table rows with an interpolated LIMIT and a bypassable table allowlist, opening a fresh driver connection per request.
  • Silent dead ends. “Press Use password” at the biometric prompt re-opened the prompt; device sign-in ground to a permanent halt.

03 · MethodHow the work was done

Everything in this report was produced under five ground rules, lifted from the spec’s own working agreement:

  1. Red first. A test is written and observed failing before the implementation exists — a test that cannot fail for the right reason is not a test.
  2. One step, one commit. Every commit names its step (spec 37 step 7.2); the tree is never left half-migrated across steps.
  3. Green tree, always. make test — copy rules, typecheck, server and client suites — passed at the end of every step.
  4. Decisions before code. Where the plan touched a recorded architectural decision, an ADR was written first (028, 029, 030), never after the fact.
  5. Move, never rewrite. The plan reordered and consolidated existing behaviour; it never “rewrote for beauty”. HTTP response shapes were preserved.
ADR = Architecture Decision Record. Short documents in decisions/NNN-slug.md that record why a choice was made and what alternatives were rejected. This repository treats them as the ranking authority over code. Three new ones were needed: 028, 029, 030.

Phase 0Foundations — the gate and the test helper

Phase 0

0.1 Typecheck into make test · 0.2 Shared request test helper

0.1 · 0.2 fe5b2ad

Before

vitest run never typechecks, so a test file importing a non-existent type passed the whole suite and only failed a manual tsc — easy to skip, and skipped. Every one of the ~40 test files stubbed fetch its own way; three of those stubs disagreed on ETags, and none could assert on what was actually requested.

After

make test now runs tsc in both packages before any test runs. A scratch probe proved the gate fails on a bad type, then was deleted. client/src/test/requests.ts provides fakeResponse() and stubFetch(); the stub records every call (URL, method, headers, body) so later phases could assert on requests, not just responses.

Why this exists — Phases 1 to 5 rewrite request- and type-heavy code under a strict “green tree” rule. Without a typecheck gate, a suite that runs but proves nothing would have sailed through.

Phase 1 · Candidate 01One request interface

The family client talked to its own server through a global monkey-patch: installApiBaseUrl() rewrote window.fetch in main.tsx, and every call site then picked one of ~8 request idioms, each with a different guarantee set. Correctness was a property of the environment, not of the call.

Phase 1

1.1 Naming the guarantees · 1.2 Points the data hooks at it · 1.3 The components · 1.4 The admin client · 1.5–1.6 The shim dies

d1521bb · 331f336 · 79473e6 · 287e256 · b2b3df3 · 8ce5409 · 316eedf

Before

  • installApiBaseUrl() monkey-patched window.fetch; a module using boundedFetch was right only because something else had run first.
  • ~30 call sites depended on the shim for base URL, session header and credentials; the native shell broke if any piece went missing.
  • The admin panel (a separate app, separate credential) had 16 raw fetch calls and a near-empty test file.
  • ProfileSwitcher.load() had no timeout and no try/catch — a failed load threw an unhandled rejection and the dropdown went silently empty.

After

  • lib/request.ts owns the five guarantees; requestConditional absorbed the 304 rule so it is no longer re-derivable per hook.
  • lib/bounded.ts holds the deadline, shared by both bundles (race + abort — a fetch that ignores its signal still loses).
  • Admin got its own admin/request.ts (separate door, separate credential), its screens split into a renderable app.tsx, and a bundle-separation test
  • Every component call-site moved; apiFetch, apiAssetUrl, and the shim itself (installApiBaseUrl) are deleted — window.fetch is unpatched.
Why this is an improvement — correctness of a request is now a property of the call, not of load order. The admin app and the family app each carry only the guarantees they need; the family client lost its single most fragile global side effect; and the interface’s guarantee set is pinned by tests that were watched failing.

Phase 2 · Candidate 02 (part 1)One offline key format

This one is a live bug, not tidiness: two servers could each hold book #7, and the device overwrote one resume position with the other — silently, with no error anywhere.

Phase 2

2.1 Proving the collision · 2.2 Server-scoped private keys

cee4ba2 (merged into master ahead of the branch)

Before

privateCache.ts stored progress under "progress", "7" while the device replica stored rows under serverId#bookId. Two servers, one key, silent overwrite. Favourites had the same defect one shape over.

After

cacheProgress/readProgress/cacheFavourites/readFavourites take a server scope and build keys via replicaBookKey/replicaScopedKey. Legacy rows are read with a fallback but not copied forward — a legacy row cannot say which server it belongs to, so copying it would hand one server’s position to another server’s same-numbered book.

Why this is an improvement — multi-server households stop corrupting each other’s state, and the failure mode changed from silent data loss to (at worst) a legacy row that is simply left behind. The fix is also the one key format in the codebase, which is what Phase 3 builds on.

Phase 4 · Candidate 03The orchestration layer gets a home

App.tsx was 1,200 lines of orchestration: the wiring between the browser, the server, the offline gates and the player — with 20 useState calls, 13 useEffects, and essentially no tests of its own. The gate ladder’s precedence was expressed only by vertical position in the file.

f254368 · 567b29b · 7d680ea · 48b6046 · 21dd211 · 97412bb · 9468585 · 4edb62e · e364c8d · f4f0fc5 · 79752d9 · 346002b

Before

  • Shelf profile and player profile were computed differently on purpose; only the variable names hinted at it.
  • Six effects raced to refresh the same shelf; nobody could state the policy.
  • The background-lock sequence — visibility listener, 30-second interval, wait-for-playback, lockLocal() — lived in App.tsx and was entirely untested.

Phase 5 · Candidate 05 · ADR 028One module owns field precedence

“User edits beat enrichment beats embedded tags beats filename guesses” is the correct order. It existed as a tested module that nothing imported, while three call sites re-derived the rule inline — and a rescan silently overwrote enriched titles with embedded ones.

Decision · ADR 028Phase 5

5.1 Deciding what the chain means · 5.2 The rule in one module

8e775af · fe0a8cc

Before

  • precedence.ts — tested, complete, dead code.
  • The override rule re-derived at scanner.ts:316, apply.ts:164, run.ts:344 — three copies, three behaviours.
  • A rescan could overwrite an enriched title with the embedded one; only user overrides survived.

After

8e10d36 · a850d21 · ce1204d · e36b535 · 84acfce · fe28a35 · 6baa4ad · b2700b8 · 19a0106

Before

DecisionsADR 028, 029, 030 — the three calls the plan needed

ADR 028

Field-level metadata precedence

decisions/028-metadata-field-precedence-chain.md · fe0a8cc

The drift: ADR 009 promised a user > enriched > embedded > derived chain; production ran “last writer wins”. The decision: keep the four-layer intent minus derived (never implemented in production); the scanner writes embedded values but must not touch a field protected by a FieldOverride, and must not overwrite an enriched value; the applier writes enriched values and honours overrides. metadataSource === "user" is retired as a protection sentinel. Enforced by: metadata/precedence.ts (canScannerWrite), imported everywhere.

ADR 029

The admin proxy belongs to the hosted, single-port deployment only

decisions/029-admin-proxy-scope.md · 19a0106

The drift: ADR 025 permits the family listener to proxy /admin for the hosted Render deployment. index.ts set adminProxyTarget unconditionally, so the household deployment also exposed /admin on the family port (and published port 3100 by default). The decision: the family listener registers no admin routes by default — the proxy is enabled only when ADMIN_PROXY=true, set only in docker-compose.prod.yml. Household: /admin answers 404. Tests cover both states.

ADR 030

Audnexus is an ASIN-keyed capability, not a title-driven provider

decisions/030-audnexus-provider-role.md · be00cd1

The drift: ADR 008 removed Audnexus from the title-driven chain; ADR 011 made it an ASIN-keyed chapter lookup. But PROVIDER_IDS still listed it and createProviders() still built it — an interface advertising a capability the chain will not use. The decision: it leaves MetadataProvider entirely; the ASIN lookup survives as a named capability (AudnexusAsin, with bookByAsin/chaptersByAsin and genre mapping unchanged). PROVIDER_IDS now lists only librivox | googlebooks | openlibrary.

08 · Safety netHow 156 files changed without breaking the house

  • The route-table snapshot test (app.test.ts) — written before the first handler moved. It derives the expected list from the app’s own onRoute hook, so it cannot drift. The split was proven to change nothing before anything changed.
  • The personal-data schema guard — reads schema.prisma, finds every model with a profileId relation, and fails if the export/erasure/purge list forgets one.
  • The typecheck gate — make test now fails on a bad type before any test runs; it caught a double-encoded body (string-in-JSON) and made it a compile error.
  • Migration safety, not migration theatre — pre-existing offline progress rows are read via a legacy fallback but deliberately not rewritten, because a legacy row cannot say which server it belonged to.
  • Both directions of the admin proxy are pinned by tests: family listener without the flag → 404 for /admin; with it → proxy.
  • Manual verification against the dev database preceded the X.8 removal of the legacy provenance sentinel (zero metadataSource = 'user' rows confirmed inside the running container).

09 · HonestyWhat is not done, and what it costs

E2E is red, and it is environmental — not a regression. The Playwright suite reports 45 passed / 8 failed; every failure traces to (a) the dev database referencing deleted ./test fixtures, so media streams answer 403, (b) a missing PWA manifest, or (c) Windows Hello being unavailable in this environment. None of the failures are in code paths this work changed. The fix is either restoring the fixtures or make reset (which wipes the dev database) — a product decision, deliberately left to the owner.
  • The Android plugin is unverified by a compiler here. BiometricVaultPlugin.java was changed as part of X.11 (all reject sites now carry a stable code; every arity used was checked against PluginCall.java). No Android SDK exists in the working environment; the next APK build must compile it. The web bundle is unaffected either way — the classifier has full vitest coverage with bridge-shaped errors.
  • Seven pre-existing copy warnings (account → profile GLOSSARY warnings in copy.ts) predate this work and were left alone; the copy check passes with warnings.
  • App.tsx did not get smaller, dramatically. The plan’s goal was testability, not deletion; the file went 1,212 → 1,110 lines. The win is the six tested modules it now delegates to.
  • The derived precedence layer stays undocumented in code by design — ADR 028 drops it from the chain instead.

10 · BoundariesOut of scope, deliberately

  • No rewrite. Every step was a move or a rule extraction — never a rewrite of a 2,000-line function “for hygiene”. HTTP response shapes were preserved.
  • No framework, state library, or test runner was introduced (no router, no React Query, no Zustand).
  • No change to the enrichment pipeline’s behaviour — LIMITATIONS §1.1/§1.2 (Open Library / Google Books reliability) are product bugs with their own specs.
  • No change to the library scanner’s throughput — roadmap item 01.
  • The admin client remains a separate app (ADR 022): separate credential, separate bundle, separate origin — now with a shared deadline rule and a shared readonly connection, never shared credentials.

Appendix ·Glossary for the uninitiated

ADR
Architecture Decision Record — a short decisions/NNN-slug.md documenting one consequential choice and the rejected alternatives.
Break-glass
The household shared password path: acceptable for setup/recovery, never the daily sign-in.
Composition root
The one place a server wires its dependencies together; here, buildApp.
Demo policy
Which routes exist when the deployment serves a public demo (most admin surfaces must 404).
ETag / 304
Conditional GET: the client asks “changed since?”, server answers “not modified” with no body — the library shelf uses it to avoid re-downloading.
Field override
A per-field human lock (“this title is Our House, full stop”); nothing may overwrite an overridden field.
GDPR export / erasure / retention
The three data-subject-rights flows this codebase supports; all read one list of personal-data tables.
Library root
A configured disk directory the scanner may read. Nothing outside a configured root is ever touched.
PWA
